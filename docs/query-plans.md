## Reading the table

- `IXSCAN` = index range scan; `FETCH` = load documents for the keys the index returned; `LIMIT`/`SKIP` run after the index already delivered the sort order, so the indexed list queries (cases 2–4) have no in-memory `SORT` stage.
- Prefix search stays index-backed because `searchTokens` holds normalised lowercase tokens and the query uses anchored, case-sensitive regexes (`/^car/`), which MongoDB turns into an index range scan. A `/car/i` or `contains` regex would be a full scan.
- Cases 1 and 5 (prefix search) use the multikey `searchTokens` index to find matches, then sort only those matches in memory: a multikey regex range cannot also deliver sort order, but the in-memory sort never touches documents that did not match the search.
- Case 6 is a covered index scan (`PROJECTION_COVERED`, 0 documents fetched).
- Case 7 aggregates every patient by design (the "top doctors" chart). A hinted covered index scan was measured and was slower than the plain collection scan, so no hint is used; the result is cached for 60 s. Scale-up path: a denormalised `patientCount` on doctors kept with `$inc`.
